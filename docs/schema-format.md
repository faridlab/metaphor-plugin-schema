# Schema Format Reference

This document covers all schema file formats, types, attributes, and syntax supported by the Metaphor schema system.

## File Types

| Extension | Purpose | Format |
|-----------|---------|--------|
| `*.model.yaml` | Entity definitions, shared types, enums | YAML (recommended) |
| `*.hook.yaml` | Entity lifecycle behaviors, state machines, rules, triggers | YAML |
| `*.workflow.yaml` | Multi-step business processes (Saga pattern) | YAML |
| `*.model.schema` | Entity definitions (legacy) | Custom DSL |
| `*.workflow.schema` | Workflow definitions (legacy) | Custom DSL |

Schema files are discovered automatically in the module's `schema/` directory:

```
libs/modules/{module}/schema/
  ├── user.model.yaml
  ├── user.hook.yaml
  ├── order.model.yaml
  ├── order.hook.yaml
  ├── order_processing.workflow.yaml
  └── index.model.yaml        # Module-level configuration
```

## YAML Model Format

The `*.model.yaml` file is the primary schema definition format. It supports the following top-level sections:

```yaml
# Data definitions
models:           # Model/table definitions
enums:            # Enumeration types
types:            # Custom reusable type definitions
generators:       # Per-file generator configuration

# DDD extensions (see ddd-guide.md)
entities:         # Enhanced models with behavior
value_objects:    # Domain-specific composite/wrapper types
domain_services:  # Services with dependencies
event_sourced:    # Event sourcing configurations
authorization:    # RBAC/ABAC permissions and roles
usecases:         # Application layer operations
events:           # Domain event definitions
projections:      # CQRS read models
services:         # Application services
handlers:         # Event handlers
subscribes_to:    # Cross-module event subscriptions
integration:      # ACL adapter definitions
presentation:     # HTTP/gRPC config
dtos:             # Request/response definitions
versioning:       # API versioning config
traits:           # Repository trait definitions
```

### Models

Define data models that map to database tables and Rust structs:

```yaml
models:
  - name: Order
    description: Customer order with line items and lifecycle status
    collection: orders          # Database table name
    soft_delete: true           # Enable soft-delete (adds deleted_at field)
    fields:
      id:
        type: uuid
        primary_key: true
      customer_id:
        type: uuid
        required: true
      email:
        type: string
        required: true
        unique: true
      status:
        type: OrderStatus       # Reference to an enum
        required: true
      total:
        type: decimal
      metadata:
        type: json
      created_at:
        type: timestamp
        auto: true              # Auto-generated by database
      updated_at:
        type: timestamp
        auto: true
    relations:
      customer:
        type: Customer
        attributes: ["@one", "@foreign_key(customer_id)", "@on_delete(restrict)"]
      items:
        type: OrderItem[]
        attributes: ["@one_to_many", "@on_delete(cascade)"]
    indexes:
      - fields: [customer_id]
      - fields: [status, created_at]
      - fields: [email]
        unique: true
```

> **Strict parsing.** Model entries reject unknown top-level keys.
> Misplacing per-model generator gating (`disabled: [...]` written at
> the model root instead of under `config.generators.disabled`) now
> fails parse with `unknown field 'disabled', expected one of …`
> instead of being silently ignored. See
> [Generators Configuration](#generators-configuration) for the correct
> shape.

### Field Properties

| Property | Type | Description |
|----------|------|-------------|
| `type` | string | Field type (primitive, enum reference, or custom type) |
| `required` | bool | Field cannot be null (default: `false`) |
| `primary_key` | bool | Mark as primary key (default: `false`) |
| `unique` | bool | Add unique constraint (default: `false`) |
| `auto` | bool | Auto-generated value (default: `false`) |
| `default` | any | Default value for the field |
| `lifecycle` | string or map | Lifecycle shape declaration (ADR-0016) — see below |

### Lifecycle (ADR-0016)

A field's `lifecycle:` declares *how its value comes to exist and change* — the
ten patterns observed across the Odoo corpus (recurring-themes A1). It is
advisory metadata for generators and reviewers in v1 (no codegen from it yet),
but its **references are validated**: a declaration naming things that don't
exist is a hard error, not a comment.

Two forms — a bare shape string:

```yaml
models:
  - name: Festival
    fields:
      state:
        type: string
        lifecycle: hand_set
```

…or the full map form with metadata:

```yaml
      sub_state:
        type: string
        lifecycle:
          shape: split          # required
          driver: stage         # split demands the stage field it splits against
          sticky: true          # once set, survives transitions that would reset it
```

The ten shapes:

| Shape | Meaning | Requirements |
|---|---|---|
| `projection` *(default)* | Stored compute re-derived from the row on every write | `driver:` optional (must name a same-model field) |
| `hand_set` | Hand-set value with a guarded transition graph | `state_machine:` must name a hook machine guarding **this** field |
| `hybrid` | Compute with a hand-set override that wins until re-derived | — |
| `split` | Sub-state field splitting against a stage field | `driver:` **required**, must name a different same-model field |
| `stage_ref` | The stage another field's lifecycle hangs off | field must carry a relation (`stage_id` ↔ relation `stage`) |
| `window` | Date-window pair field (from/until) | — |
| `virtual` | Never stored — computed at read | — |
| `label` | Mirrors or summarizes another field; no lifecycle of its own | — |
| `inert` | Set once at creation, never meaningfully transitions | — |
| `none` | Explicitly no lifecycle | — |

Optional metadata keys: `sticky`, `latched` (clearable only by a declared
action), `display_labels` (map of stored value → label; the stored value is the
contract), `driver`, `state_machine`.

Unknown shape names are a **named conversion error** (`unknown lifecycle shape
'…' (expected one of …)`) that names the offending field. Fields without a
`lifecycle:` key are untouched — existing schemas are unaffected.

### Entity lifecycle fields (status enums)

An entity's lifecycle state is **one `status` enum field** — never a boolean
impostor (`is_active`, `is_archived`), never a jsonb blob for a group of
columns that carry FKs. Rules:

- Model a lifecycle as an enum whose variants are the real states the workflow
  distinguishes (start from `active` / `inactive`; add `draft`, `cancelled`, …
  only when a workflow demands the distinction — a boolean can only ever hold
  two of them, and every extra boolean multiplies the invalid state space).
- One default variant, declared `default: true`, matching the column default
  the migration installs (`'active'`).
- Migrations that create these enum types MUST create them **unqualified**
  (`CREATE TYPE bank_status …`, not `CREATE TYPE banking.bank_status`): the
  generated sqlx enums carry an unqualified `type_name`, and a schema-qualified
  type makes Postgres describe columns as `schema.type`, so native decode fails
  with a mismatched-types error on any select that doesn't cast `::text`.
- Flipping an existing boolean: migrate only rows deviating from the boolean's
  own column default (`UPDATE … SET status = 'inactive' WHERE NOT is_active`),
  never an unconditional true→active / false→inactive rewrite; pair every up
  with a restore-down.

### Enums

Define enumeration types:

```yaml
enums:
  - name: OrderStatus
    variants:
      - Pending
      - Confirmed
      - Shipped
      - Delivered
      - Cancelled

  - name: UserRole
    values: [admin, editor, viewer]    # Alternative short syntax
```

Enum names are automatically converted to **PascalCase** in generated Rust code:

```yaml
# Schema
enums:
  - name: relationship_type
    values: [lead, customer, partner]

# Generated Rust
# pub enum RelationshipType { Lead, Customer, Partner }
```

PascalCase conversion splits on `_`, `-`, and spaces, so a hyphenated or spaced
name still produces a valid Rust identifier — `serpa-posman-service` becomes
`SerpaPosmanService`, not `Serpa-posman-service`. `snake_case` remains the
recommended convention for schema names; the extra separators exist so that names
carried in from elsewhere (a project or package name, for instance) convert
cleanly rather than emitting code that will not compile.

### Shared Types

Define reusable type compositions:

```yaml
types:
  - name: AuditFields
    fields:
      created_at:
        type: timestamp
        auto: true
      updated_at:
        type: timestamp
        auto: true
      created_by:
        type: uuid
      updated_by:
        type: uuid
```

### Generators Configuration

Control which generators run at the file level:

```yaml
generators:
  enabled: [rust, sql, repository]     # Whitelist mode
  disabled: [cqrs, projection]         # Blacklist mode
  cqrs: true                           # Explicit opt-in for a specific target
```

**Resolution rules:**

- `enabled` and `disabled` are mutually exclusive — pick one mode per file.
- Per-target booleans (`cqrs: true`, `event-store: false`) override the
  `enabled` / `disabled` lists, so you can use a list as the baseline
  and toggle individual targets on top.
- Target names match the canonical names from the per-platform docs
  (e.g. [generate-rust.md](generate-rust.md) target tables). Aliases
  (`gql` for `graphql`, `migration` for `sql`, etc.) are accepted.

**Off by default:** a target nothing in a module or its host uses is generated
only when the module turns it on. `opt_in:` lists them by target name (aliases
work, and listing one in `enabled:` counts too):

```yaml
generators:
  opt_in: [seeder, versioning]
```

| Target | Why it is off |
|---|---|
| `versioning` | no generated module mounts the API version router |
| `seeder` (Rust half) | `metaphor migration seed` runs the SQL seeds; the Rust seeders (`src/seeders`, the seeder binary) are only its fallback. The SQL seeds in `migrations/seeds` are still generated by default |
| `graphql`, `grpc`, `proto` | no module serves these transports |

CQRS (`cqrs: true`) and the composition layers (`layers: true`) are off by
default too, through their own flags. Retired targets generate nothing even when
named: `trigger`, `specification`, `validator` and `usecase`, and the `workflows:` flag.
`schema validate` warns about each. The `workflow` target generates only for a workflow that says
`config.executor: engine` (see [Workflow YAML Format](#workflow-yaml-format)); a module that lists it under
`disabled:` beside such a workflow fails validation.

**Cross-target side effects:**

Some Rust targets emit wiring that depends on whether sibling targets
were generated. The `module` target (which writes `lib.rs`) tracks the
effective enabled set and **drops** the router-mount, gRPC service
registration, and `MergedObject!` entries when `grpc` or `graphql` is
disabled — so the module still compiles when only a subset of
transports is in use. The full list of cross-target dependencies is in
[generate-rust.md → module](generate-rust.md#module----module-wiring-librs--modrs).

**Per-model overrides:**

Individual model entries accept the same `enabled` / `disabled` lists,
either as a direct `generators:` field or wrapped under `config:` to
mirror the file-level shape:

```yaml
models:
  audit_log:
    generators:
      disabled: [cqrs, graphql]   # skip CQRS + GraphQL for this one model
    fields: { ... }

  read_only_view:
    config:
      generators:
        enabled: [rust, sql]      # only emit the data layer for this entity
    fields: { ... }
```

When both forms appear on the same entry, the direct `generators:` field
wins. Models that opt out of a target are dropped wholesale from that
target's output — no file is written and no entry appears in the
generated parent `mod.rs`.

See the per-platform docs for the full target catalog:

| Platform | Target list |
|----------|-------------|
| Rust server | [generate-rust.md § Generation Targets](generate-rust.md#generation-targets) |
| Kotlin mobile | [generate-kotlin.md § Targets](generate-kotlin.md) |
| Webapp (TS+React) | [generate-webapp.md § Targets](generate-webapp.md) |

## Field Attributes

Used in the legacy DSL format and in relation `attributes` arrays:

| Attribute | Description | Example |
|-----------|-------------|---------|
| `@id` | Primary key | `id uuid @id` |
| `@unique` | Unique constraint | `email string @unique` |
| `@required` | Not nullable | `name string @required` |
| `@default(value)` | Default value | `@default(now)`, `@default(uuid)`, `@default(active)` |
| `@min(n)` | Minimum length/value | `@min(3)` |
| `@max(n)` | Maximum length/value | `@max(255)` |
| `@pattern(regex)` | Regex validation pattern | `@pattern([a-z0-9-]+)` |
| `@precision(p, s)` | Decimal precision/scale for `NUMERIC` columns. Emits `NUMERIC(p, s)` in the generated DDL (a lone arg emits `NUMERIC(p)`); without it a `decimal`/`money` field is a bare, unbounded `NUMERIC`. Applies to any type that maps to `NUMERIC`. | `amount money @precision(12, 2)` |
| `@non_negative` | Emits a column `CHECK (<col> >= 0)` in the generated DDL, so every writer (not just the hand-authored write service) is blocked from storing a negative value. The CHECK passes for `NULL`, so it is safe on optional fields. | `balance decimal @non_negative` |
| `@foreign_key(ref)` | Foreign key reference | `@foreign_key(User.id)` |
| `@soft_delete` | Enable soft-delete on model. On the Kotlin side, when paired with an `@audit_metadata` field, the entity gains a derived `val isDeleted: Boolean get() = metadata["deleted_at"] != null` helper. If the schema also declares an explicit `is_deleted` column, the helper is suppressed (the column wins) so there is exactly one canonical `isDeleted` property. | - |
| `@hashed` | Field is stored hashed (e.g., passwords) | `password string @hashed` |
| `@audit_metadata` | JSONB audit metadata field. On the Kotlin side this is emitted as the `Metadata` typealias (`Map<String, JsonElement?>`), not raw `JsonElement` — see [generate-kotlin.md](./generate-kotlin.md). | - |
| `@omit_if_none` | Omit this nullable field from the serialized response when its value is `None` (emits `#[serde(skip_serializing_if = "Option::is_none")]`). By default nullable fields serialize as explicit `null` for a stable response shape; use this attribute to opt out per field. | `deleted_at datetime? @omit_if_none` |
| `@private` | Field-level security: the field is pruned from serialized responses for non-owner/non-root callers. Collected into the generated `EntityRepoMeta::private_fields()` override (as camelCase response keys); backbone-core's `apply_field_security` strips these keys at the handler. | `ssn string @private` |
| `@owner` | Marks the tenant/ownership column used by field-level security to decide who counts as the owner. Emitted as the `EntityRepoMeta::owner_field()` override (camelCase response key). At most one per model. | `user_id uuid @owner` |
| `@global` | Opts a `company_id` column **out** of the company fence — see [Company Scoping](#company-scoping) below. Use it only on genuinely cross-company reference data. | `company_id uuid @global` |
| `@immutable` | Field cannot be changed via generic CRUD after creation: excluded from the generated `Update*Dto` and `Patch*Dto` (and the derived `has_changes` / `ApplyUpdateDto` impls), so engine-managed state (status, costs, journal ids, …) can't be mutated through the generic PATCH/PUT surface. Still present in `Create*Dto` and `*ResponseDto`; an engine that writes via the repository directly is unaffected. | `status VisitStatus @immutable` |
| `requires:` (field key) | Field-level permission gate (ADR-0033, second amendment): `requires: "<resource>:<action>"` on a field names the permission a caller must hold to see and set it. The generated entity emits `EntityRepoMeta::field_permissions()` (camelCase key, canonical permission) and the webapp schema `<Entity>FieldPermissions`. For a non-holder the value is redacted to `null` (the key stays — indistinguishable from a stored null) on every read surface including `?include=` expansions and the history answers; a filter/sort/search/aggregate naming it is refused `400 invalid_query` reason `field_permission`; a write naming it (either casing) is refused `422 field_permission_required` with `params.permission`. `*:*` and wildcards hold everything. The permission must be in the vocabulary (declare it under `authorization: permissions:` when no route implies it), and a field that is also `@sensitive`/`@hashed` is an error. `schema rules` labels it `FIELD REQUIRES <permission>`. | `base_salary decimal? requires: "employee:read_confidential"` |
| `@searchable` | Adds this field to the entity's `?search=` set (`EntityRepoMeta::search_fields()`), widening the derived default (required `string`/`email`/`slug` fields) — the way an **optional** text field becomes searchable. The field must be one of those text kinds (optional included); on a secret (`@sensitive`/`@hashed`) or permission-gated (`requires:`) field it is an error, and a gated field is excluded from the derived set regardless — `?search=` is a substring match served to any caller holding the route's read, so a searchable gated field would let a non-holder probe the value one character at a time. A model-level `search:` list replaces the whole set, so `@searchable` on a field the list does not name is an error (dead attribute). `schema rules` labels the model `SEARCH <fields> declared (@searchable)`. | `email string? @searchable` |
| `search:` (model key) | Declares the **whole** `?search=` field list for the model, in the emitted order, replacing the derived set (required text fields plus `@searchable` fields). Every name must be a `string`/`email`/`slug` field of the model (optional included) that is neither a secret nor permission-gated (`requires:`) — the same refusals as `@searchable` — and listing a name twice is an error. This is how a module whose entity file was user-owned only to widen search (optional `last_name`/`email`) returns the file to generated. `schema rules` labels the model `SEARCH <fields> declared`. | `search: [employee_number, first_name, last_name, email]` |

## Relation Attributes

| Attribute | Description |
|-----------|-------------|
| `@one` | One-to-one relationship |
| `@many` | One-to-many relationship |
| `@one_to_many` | One-to-many (explicit) |
| `@many_to_many` | Many-to-many relationship |
| `@belongs_to` | Inverse relationship |
| `@references(column)` | Custom referenced column |
| `@join_table(name)` | Many-to-many join table name |
| `@join_fk(column)` | Many-to-many FK column |
| `@foreign_key(column)` | Explicit FK column name |

### Relation Examples

```yaml
relations:
  # One-to-one
  profile:
    type: Profile
    attributes: ["@one"]

  # One-to-many with cascade delete
  items:
    type: OrderItem[]
    attributes: ["@one_to_many", "@on_delete(cascade)"]

  # Many-to-many with custom join table
  roles:
    type: Role[]
    attributes: ["@many_to_many", "@join_table(user_roles)", "@join_fk(user_id)"]

  # Belongs-to with foreign key
  customer:
    type: Customer
    attributes: ["@belongs_to", "@foreign_key(customer_id)", "@on_delete(restrict)"]
```

## Indexes

In YAML format:

```yaml
indexes:
  - fields: [email]                    # Single-field index
    unique: true
  - fields: [status, created_at]       # Composite index
  - fields: [customer_id]
```

In legacy DSL format:

```
indexes {
    @@index(email)
    @@index(status, created_at)
    @@unique(resource, action)
}
```

### Partial Indexes

Use the `@where` attribute to emit a partial index — the predicate is appended
verbatim as a SQL `WHERE` clause:

```yaml
indexes:
  - fields: [email]
    unique: true
    attributes: ['@where(deleted_at IS NULL)']
```

**Audit-metadata rewriting.** When the model carries an `@audit_metadata`
JSONB field, audit keys (`created_at`, `updated_at`, `deleted_at`,
`created_by`, `updated_by`, `deleted_by`) are stored *inside* that JSONB
column, not as real columns. To keep the predicate readable, bare
identifiers matching those keys are rewritten to their JSONB form
(`(metadata->>'deleted_at')`). String literals and identifiers already
qualified (e.g. `t.deleted_at`) are left alone, and a model that declares
one of those names as a real column shadows the rewrite.

```yaml
# Authored:
attributes: ['@where(deleted_at IS NULL)']

# Emitted (model has @audit_metadata field `metadata`):
WHERE (metadata->>'deleted_at') IS NULL
```

## Company Scoping

A model that declares a `company_id` column is **company-scoped**, and the `sql` target
fences it with a Postgres Row-Level-Security policy (ADR-0008). Nothing needs to be
opted in: the presence of the column is the signal, so a newly added entity is fenced by
default and forgetting to think about tenancy fails safe.

For each such table the generator emits, into a per-module
`<ts>_enable_company_rls` migration that runs after every `CREATE TABLE`:

```sql
ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;
ALTER TABLE invoices FORCE  ROW LEVEL SECURITY;
DROP POLICY IF EXISTS invoices_company_isolation ON invoices;
CREATE POLICY invoices_company_isolation ON invoices
    FOR ALL
    USING      (company_id = NULLIF(current_setting('app.company_id', true), '')::uuid)
    WITH CHECK (company_id = NULLIF(current_setting('app.company_id', true), '')::uuid);
```

(The table reference is schema-qualified — `billing.invoices` — when the model declares
a `schema:`, and the policy name is derived from the bare table name.)

The generated Rust also carries the same fact as
`EntityRepoMeta::company_field()`.

**Scoping a request.** The application sets the session var per request:

```sql
SELECT set_config('app.company_id', '<uuid>', true);  -- true = transaction-local
```

An unset var — or one a prior `set_config` left as the empty string — collapses to
`NULL` through the `NULLIF`, and `company_id = NULL` matches **zero rows**. The fence
fails closed: a request that forgets to scope itself sees nothing, rather than seeing
everything or erroring on a `''::uuid` cast.

**The app must connect as a non-superuser role.** `FORCE` extends the policy to the
table owner, but superusers always bypass RLS. Migrations and seeders run as the
owner/superuser and are the deliberately unfenced system path.

`WITH CHECK` gives write-side symmetry — a request scoped to company A cannot INSERT a
row owned by company B.

**Opting out with `@global`.** Genuinely cross-company reference data marks its column
`@global`, and no policy is generated for that model:

```yaml
fields:
  company_id: { type: uuid, attributes: ['@global'] }   # shared reference data
```

A model with no `company_id` column at all is likewise unfenced, and a module with no
company-scoped models emits no RLS migration file. Because the fence lives in its own
additive, idempotent migration (`ENABLE` + `DROP POLICY IF EXISTS`), it applies equally
to a fresh database and as a retrofit onto tables that already exist.

### Company Fence (ADR-0014)

The template above is the **strict** fence — the default when nothing is declared. A
module can declare a different posture in `index.model.yaml`:

```yaml
module: catalog
schema: catalog
company_fence: shared_blank   # strict | shared_blank | shared_tree | none
```

| Value | Meaning | `USING` / `WITH CHECK` |
|---|---|---|
| `strict` *(default)* | Rows visible only within the declaring company | `company_id = <session var>` |
| `shared_blank` | Master data: NULL-company rows are **shared** with every company; non-NULL rows stay fenced | `company_id = <var> OR company_id IS NULL` |
| `shared_tree` | Hierarchical: rows visible within the company **subtree** rooted at the declaring company | `company_id IN (SELECT company_id FROM organization.company_subtree(<var>))` |
| `none` | No company dimension at all — **nothing is emitted** | — |

Compatibility and rules:

- **Undeclared = `strict`, byte-identical.** Modules predating the key produce exactly
  the same migrations as before (test-enforced).
- **`@global` still wins per model** under any declaration — a `@global company_id`
  column unfences that one model even in a `shared_blank` module.
- **`none` + a non-`@global` `company_id` column is a hard validation error.** That
  combination would silently unfence every row the module stores; fix it per model
  (`@global`, drop the column, or pick a real fence). This is the one fatal case —
  the other oddities (a declared fence with no fenced model; `shared_blank` where
  every `company_id` is NOT NULL, making the shared arm dead) are printed as
  warnings by `validate` and `generate`.

For `shared_tree`, the migration also ships a helper function exactly once, before any
policy that reads it:

```sql
CREATE OR REPLACE FUNCTION organization.company_subtree(root uuid)
RETURNS TABLE (company_id uuid)
LANGUAGE sql
STABLE
AS $$
    WITH RECURSIVE tree AS (
        SELECT c.id AS node_id
        FROM organization.companies c
        WHERE c.id = root
        UNION ALL
        SELECT c.id
        FROM organization.companies c
        JOIN tree t ON c.parent_company_id = t.node_id
    )
    SELECT node_id FROM tree
$$;
```

Convention: the hierarchy is `organization.companies(parent_company_id)`, the subtree is
**root-inclusive**, and `company_subtree(NULL)` returns **no rows** — so an unscoped
session sees nothing under every template (fail-closed is uniform). The down migration
drops the function (`DROP FUNCTION IF EXISTS organization.company_subtree(uuid);`).

## Soft Delete

Enable soft-delete on a model to automatically generate:
- A `deleted_at` timestamp field
- Trash listing endpoints
- Restore endpoint
- Repository methods with soft-delete filtering

```yaml
models:
  - name: User
    collection: users
    soft_delete: true
    fields:
      # ... deleted_at is added automatically
```

A model is treated as soft-deletable in two ways:

1. **Explicit** — `soft_delete: true`.
2. **By convention (Backbone)** — the model carries an audit `metadata` field or
   a `deleted_at` field. The Backbone backend exposes the trash endpoints for
   exactly these entities, so the generator infers soft-delete automatically and
   emits the trash use cases.

Soft-deletable entities gain the trash surface in the generated webapp runtime:
`listDeleted`, `restore`, `emptyTrash` (`DELETE /empty`), and `permanentDelete`.
A plain `delete` performs the soft delete itself, so there is no separate
`softDelete` operation.

## Hook YAML Format

The `*.hook.yaml` files define entity lifecycle behaviors:

```yaml
hooks:
  OrderHooks:
    entity: Order

    states:
      - name: pending
        initial: true
        on_enter:
          - action: send_notification
            params: { template: "order_created" }
      - name: confirmed
      - name: shipped
      - name: delivered
        final: true
      - name: cancelled
        final: true

    transitions:
      - from: pending
        to: confirmed
        guard: "has_payment"
        roles: [admin, manager]
      - from: confirmed
        to: shipped
        roles: [admin, warehouse]
      - from: shipped
        to: delivered
      - from: [pending, confirmed]
        to: cancelled
        roles: [admin, customer]

    rules:
      minimum_order_amount:
        when: [create, update]            # create | update | delete (optional)
        condition: "order.total >= 10.00"
        message: "Order total must be at least $10.00"
        code: "ORDER_BELOW_MINIMUM"       # optional — warnings often omit it
        severity: error                   # error | warning (optional)
        enforcement: db                   # db | service | both (ADR-0015, optional)
        # justification: mandatory when enforcement: service — why the invariant
        # lives in the service layer instead of the database, e.g.:
        #   justification: "cross-model check; needs both rows in memory"

    permissions:
      customer:
        allow:
          - read                          # shorthand: bare action string
          - action: update                # full form: condition + field scope
            if: "order.status == 'pending'"
            only: [items, shipping_address]
        deny:
          - action: update
            except: [total]               # all fields except these
      admin:
        allow:
          - all

    computed:
      - name: total
        expression: "sum(items.price * items.quantity)"
        type: decimal

events:
  OrderConfirmed:
    when: "the order is confirmed"
    payload: [order_id, company_id, confirmed_at]
```

**Triggers run in the write's transaction** (ADR-0034). A hook's `triggers:` and a state's
`on_enter` / `on_exit` lists are generated into the model's write hooks. A key is
`before_` or `after_` with `create`, `update` or `delete`; `after_update_<field>[_<value>]`
(the field changed, to that value when one is named); `after_<verb>` of the model's state
machine; a free key with `timing:` (the event) or `schedule:` (a job); `entity:` binds an entry
to another model of the file; `if:` (alias `condition:`) guards it.

```yaml
triggers:
  before_create:
    actions:
      - "set: sla = 'standard'"                      # fills the row before it is stored
  after_update_status:
    if: "status != $old.status"
    actions:
      - "log(ticket.moved, { id: id })"              # a line carrying the correlation id
      - "emit: TicketMoved(ticket_id: id)"           # the declared event, staged in the transaction
      - "send_email(moved, owner_email)"             # a NotificationRequested outbox row
      - "trigger: refresh_counters"                  # anything else: a required trait method
```

What compiles runs (`emit:`, `log`, `set:` / `increment:` before the write, `send_email`, `notify`,
`if: cond { action }`); everything else becomes a method of the generated
`<Model>Triggers` trait with no default body, implemented as `<Model>TriggersImpl` in
`<model>_triggers.ext.rs` (so the module needs `generators: extensions: true`). A trigger that fails
rolls the write back with everything it staged. `schema rules` shows what each trigger does and
`schema doctor` what hand code owes. A module that sets `generators: legacy_triggers: true` keeps
the old behaviour: nothing is generated and `schema validate` warns.

**Events are a contract.** `events:` names what the module publishes, with when and what payload,
and generates a typed payload per event. An event with `on:` is staged by the model's write hooks; one a
trigger `emit:`s is staged by that trigger; the service stages any other by hand, in its write's
transaction. `schema doctor` reports a declared event nothing stages.

**Public reference data.** A model declares `public: true` (the reads) or `public: [read, ...]` to
serve those generic actions without a permission or a login where the host mounts the module's
`public_routes()` outside its authentication layer; `public_scoped: true` acknowledges a fenced
model (ADR-0033, amendment).

Both the rich map-based form shown above and the canonical list/sequence
authoring form are accepted everywhere `*.hook.yaml` is consumed. The webgen
generator tries the map form first and falls back to the canonical flexible
parser, so it accepts exactly the same hook grammar as the backend codegen — an
authored hook parses in every generator regardless of which spelling it uses.

### Rule enforcement (ADR-0015)

Every rule carries an `enforcement:` declaration saying **where its invariant
holds** — the declaration is the review surface for the raw-SQL-bypass risk:

| Value | Meaning |
|---|---|
| `db` *(default)* | Database constraint (`@unique` / `@non_negative` / `@jsonb_schema` …) — the historical behavior |
| `service` | Service-layer guard only. **Requires `justification:`** (empty/whitespace is a hard validation error). A raw-SQL write path can bypass it — the justification is what makes that a reviewed decision |
| `both` | DB backstop + service guard (e.g. for a better error message) |

Notes:

- Absent key = `db` — existing schemas are unaffected.
- v1 emits no SQL *from* a rule's `condition`; a `db`-declared invariant still
  rides the constraint attributes. Condition→SQL compilation and the
  raw-SQL-reachability lint are planned follow-ups (ADR-0015's hard lint).

### Scheduled Jobs (ADR-0020)

`index.hook.yaml` may declare module-level scheduled jobs. Jobs reach the module
schema (they used to be dropped at load time) and carry the ADR-0020 posture
vocabulary:

```yaml
module: mail

scheduled_jobs:
  mail_queue:
    schedule: "*/5 * * * *"       # cron or interval — the FLOOR, not the contract
    handler: mail::drain
    posture: self_arming          # what re-arms the job (see table)
    triggers:                     # required when posture: self_arming
      - message.created
      - message.retried
    commit_policy: commit_per_batch
    pickup_lock: true             # handler claims rows FOR UPDATE SKIP LOCKED
```

The six postures — the observed scheduler patterns (ADR-0020):

| Posture | Meaning | Needs `pickup_lock: true`? |
|---|---|---|
| `pull` | Plain interval-driven scan | **Yes** |
| `self_arming` | Domain events re-arm the schedule; interval is a floor — `triggers:` **required** | **Yes** |
| `host_riding` | No cron of its own; rides a host module's scheduler | **Yes** |
| `read_time_lazy` | No cron at all; work happens on read | exempt |
| `inactive_then_icp` | Shipped inactive; activated by post-install/ICP hooks | exempt |
| `autovacuum_ride` | GC work riding the shared autovacuum | **Yes** |

Validation:

- A job with **no posture** warns (the schedule alone doesn't say what re-arms
  the job); it never errors, so the ~60 legacy modules are unaffected.
- `self_arming` with empty `triggers:` is a **hard error**.
- A queue-draining posture without `pickup_lock: true` is a **hard error**
  (MMB-4 class: concurrent workers double-process the same rows). Claim intake
  with `FOR UPDATE SKIP LOCKED` or pick an exempt posture.
- `commit_policy` is declarative in v1: `commit_per_batch` (bounds the replay
  window, loses atomicity) vs `single_transaction` (atomic, unbounded replay on
  crash). The queue-drain-pattern refinement is a planned follow-up.

## Workflow YAML Format

A `*.workflow.yaml` file describes a business process: an event starts it, steps write through entities,
waits pause it for an event or a timer, and compensation undoes what completed. What happens to the file
depends on `config.executor`:

| `config.executor` | What it means | What is generated |
|---|---|---|
| absent or `hand` | a hand-written service runs it; the file documents it | nothing. `schema validate` says it is documentation only |
| absent or `hand`, with `implemented_by: "<file>::<fn>"` | a saga a hand service already carries out; the key names the function | nothing; `schema doctor` fails when the function does not exist |
| `engine` | `backbone-core`'s workflow engine runs it ([ADR-0035](../../docs/handbook/adr/0035-workflow-engine.md)) | `src/application/workflows/<name>_workflow.rs`, the module's `workflows/mod.rs`, a migration for the engine's tables, and `background_tasks()` on the module |

A workflow that runs on the engine:

```yaml
name: PasswordReset
version: 1

trigger:
  event: PasswordResetRequestedEvent        # an outbox event of this type starts an instance
  extract:                                  # context keys filled from the event
    email: "event.email"

config:
  executor: engine
  timeout: 1h                               # the instance's deadline; passing it while waiting ends it `expired`
  persistence: true                         # false: the whole flow in one transaction, no waits
  retry: { max_attempts: 3, backoff: exponential }

functions:                                  # calls an expression may make, implemented by hand
  - get_user_email

context:
  user: null

steps:
  - name: find_user
    type: action
    action: query                           # an entity action goes through the entity's generated service
    entity: User
    params: { email: "{{ context.email }}" }
    on_success: { set: { user: "{{ result }}" }, next: check_active }
    on_failure: { next: unknown_email }     # a business failure (not found, refused) is routed, not retried

  - name: check_active
    type: condition
    conditions:
      - if: "context.user != null && context.user.status == 'active'"
        next: generate_token
      - else:
        next: unknown_email

  - name: generate_token
    type: action
    action: generate_token                  # not an engine or entity action: a required method of <Name>Actions
    params:
      user_id: "{{ context.user.id }}"
      send_to: "{{ get_user_email(context.user.id) }}"   # a function listed under `functions:`
    on_success: { next: await_change }

  - name: await_change
    type: wait
    wait_for:
      event: PasswordResetCompletedEvent
      condition: "event.user_id == context.user.id"   # equalities on the event, joined by `&&`: the wait's key
      timeout: 1h
    on_event:   { next: done }
    on_timeout: { next: expired }

  - { name: done,          type: terminal, status: completed }
  - { name: unknown_email, type: terminal, status: completed }
  - { name: expired,       type: terminal, status: expired }

compensation:                               # runs, last first, when the instance fails
  - name: log_failure
    condition: "steps.generate_token.completed == true"
    action: audit_log
    params: { action: password_reset_failed }
```

**Step types the engine runs:** `action`, `transition`, `condition`, `wait`, `terminal`. The five the AST also
knows (`parallel`, `loop`, `subprocess`, `human_task`, `transaction_group`), a trigger by `endpoint` or
`schedule`, and workflow-level `on_success` / `on_failure` are generation errors under `engine`; so is any key
the engine does not read.

**Actions.** Engine actions need no code: `audit_log` (a log line and the step-log row), `emit_event` (stages a
declared event; `params: { event: <Name>, data: {..} }`), `send_email`, `notify`, `send_notification` and
`send_sms` (stage a `NotificationRequested`). Entity actions go through the entity's generated service, so its
guard, hooks, triggers and declared events apply: `create` (the parameters are the create DTO's fields, as the
HTTP API names them), `update` and `delete` (named by `id:`), `find_by_id`, `query` (the first row matching the
parameters as equality filters) and `fetch` (with `id:`, or with `filter:`, `order:` and `limit:` for all rows).
A `transition` names the record with `id:` and a verb of the entity's machine; it makes the generated route's
checks and is allowed only for a machine with `verbs: generated`. Anything else is a **bespoke verb**: one
required method of the generated `<Name>Actions` trait, `async fn <verb>(&self, ctx: &WriteCtx, params:
&Value, wf: &Value) -> ServiceResult<Value>`, implemented as `<Name>ActionsImpl` in
`<name>_workflow.ext.rs`. The module needs the extension layout (`generators: extensions: true`).

**Expressions** (conditions, `set:` values, `{{ }}` templates) are a closed set, compiled when the module is
generated: paths into `context`, `event` (the latest event), `result` (the step's own result, in `set:`),
`error` (the failure that was routed) and `steps.<name>.completed`; literals and durations (`15m`, `24h`,
`30d`); `== != < <= > >=`, `&& || !`, `+ - * / %`, `??`, `a ? b : c`, `x in [..]`; `.length`, `.contains()`,
`.includes()`, `.starts_with()`, `.ends_with()`, `x[0]`; `now()`, `new_uuid()`, `coalesce()`, `len()`. A bare
name reads the context key of that name when the workflow writes it (under `context:`, `trigger.extract` or any
`set:`). A call of any other function is an error unless it is listed under `functions:`, which adds a
required method `fn_<name>(&self, ctx, args)` to the trait.

**Waits** resume on the event whose payload fields equal the context values the condition names
(`event.<field> == <context expression>`, several joined by `&&`); any other condition is an error. A wait with
only a `timeout` is a timer. A wait names `on_event` and, with a timeout, `on_timeout`.

**Failure.** A step that is refused for a reason the caller can fix (not found, validation, a violation) takes
`on_failure.next` (and `on_failure.set`), or fails the instance. Any other failure retries (`on_failure.retry`
and `backoff`, else `config.retry`, else three attempts with exponential backoff), then takes
`on_failure.on_exhausted` or `.next`, else fails the instance, which compensates. `on_failure.next` can name a
step that logs and ends. A terminal's `status` is `completed`, `failed`, `expired` or `cancelled`;
`compensate: true` on a failed terminal runs compensation; `emit:` stages an event; `result:` is stored as
`context.result`.

**Checks at generation.** Every `next` names a step; every entity is a model of the module; every transition is
a verb of that entity's generated machine; every event a step emits is declared under `events:` (a trigger or
awaited event may belong to another module and only warns); an `update` or `delete` names its record. A
workflow that cannot run fails validation naming its step. Wiring: the composing service forwards the events
of `background_tasks().subscribed_events()` to `background_tasks().deliver` (the relay's sink), runs
`background_tasks().timer_sweep` as the job `workflow_timer_sweep` every minute, and runs the generated
`migrate_outbox` at startup. A module that owns its `lib.rs` or `application/mod.rs` declares
`pub mod workflows;` and builds the engine itself with `build_background_tasks`.

**Tenancy.** The engine tables carry `company_id` and the org unit of the event that started the instance. A
module that declares an `org_fence` gets them fenced by org unit; the engine acts under the instance's company
and unit (the outbox record carries the unit). A service that installs org fencing through its `tenancy.yaml`
lists `bb_workflow_instances` and `bb_workflow_steps` there as `migration_only` tables with their schema.

`schema rules` labels each workflow `WORKFLOW RUNS (on <Event>, persisted | one transaction,
executor=engine)`, `WORKFLOW DOCUMENTS (<file>::<fn>)` or `WORKFLOW DOCUMENTED`, and lists the hand methods an
engine workflow requires; `schema doctor` fails on a missing extension file or method.

## Legacy DSL Format

The legacy `.model.schema` format uses a custom DSL syntax. It is still supported for backward compatibility but YAML is recommended for new schemas.

### Model Definition

```
model User {
    collection: users

    fields {
        id          uuid        @id @default(uuid)
        email       email       @unique @required
        username    string      @unique @required @min(3) @max(50)
        password    string      @required @min(8)
        status      Status      @default(active)
        created_at  datetime    @default(now)
        updated_at  datetime?
        deleted_at  datetime?
    }

    relations {
        profile     Profile     @one
        roles       Role[]      @many_to_many
    }

    indexes {
        @@index(email)
        @@index(username)
        @@index(status, created_at)
    }
}
```

### Enum Definition

```
enum Status {
    active      @default @label("Active User")
    inactive    @label("Inactive User")
    pending     @label("Pending Verification")
    suspended   @label("Suspended Account")
}
```

### Workflow Definition (Legacy)

```
workflow OrderApproval {
    states {
        pending     @initial
        approved
        rejected    @final
    }

    transitions {
        pending -> approved [role: manager]
        pending -> rejected [role: manager]
    }

    rules {
        rule minimum_amount {
            condition: "order.total >= 100"
            error: "Orders below $100 do not require approval"
        }
    }
}
```

### Key Differences from YAML

| Feature | Legacy DSL | YAML |
|---------|-----------|------|
| Nullable types | `datetime?` suffix | Omit `required: true` |
| Attributes | Inline `@attr` syntax | `attributes` array or field properties |
| Enums | `enum Name { ... }` block | `enums:` list with `variants` |
| Relations | Inline in `relations { }` block | `relations:` mapping |
| DDD extensions | Not supported | Full support (entities, VOs, services, etc.) |
| Shared types | Not supported | `types:` section |
